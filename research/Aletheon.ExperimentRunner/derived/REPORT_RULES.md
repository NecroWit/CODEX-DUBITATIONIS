# Правила сохранения производных отчётов Aletheon

## Назначение

`derived/` содержит **аналитические отчёты** по результатам экспериментов, а не первичные ответы моделей и не состояние управления Runner. Первичные результаты, протоколы запусков, фактические расходы и ответы остаются в `runs/`. Отчёт можно пересчитать или пересмотреть, не изменяя исходные данные.

Предыдущие отчёты и их визуализация сохранены **без изменения содержания** в `derived/Depricated/` (имя папки намеренно соответствует принятому запросу). Архив не является источником новых оценок и не должен автоматически подменять актуальный отчёт.

## Ответственный и порядок подготовки

**Автор аналитического отчёта — ChatGPT (ассистент), вручную после каждого завершённого эксперимента.** Runner только выполняет эксперимент и сохраняет первичные данные; он не должен автоматически выставлять оценки, генерировать выводы или формировать аналитический отчёт.

После каждого эксперимента ассистент изучает сохранённые ответы обеих моделей, условия H1/H2, замороженные ответы Алетеона C и фактические usage/стоимость, затем самостоятельно оценивает аргументацию и соответствие C, записывает краткий вывод и сохраняет отчёт в `derived/`. Оценки являются обоснованными исследовательскими суждениями ассистента, а не машинно вычисленными метриками. Если эксперимент завершён частично, отчёт фиксирует доступные результаты и причины отсутствующих оценок.

Подготовка отчёта выполняется при разборе результатов в диалоге с ассистентом: сам по себе запуск Runner не инициирует работу ассистента и не гарантирует появления отчёта без предоставленного ему доступа к новым результатам.

## Обязательные показатели

Для **каждой пары «эксперимент — модель»** отчёт содержит четыре независимых поля:

1. **Средняя фактическая цена токена.** При наличии проверяемых данных о расходах и токенах: `sum(actual_cost_usd) / sum(prompt_tokens + completion_tokens)` по ответам данной модели в данном эксперименте. Указать USD/token и, для удобства, USD/1M tokens; это **взвешенная по числу токенов** величина, а не среднее тарифов input/output. Зафиксировать число учтённых запросов, источник usage и наличие/отсутствие учтённых reasoning tokens. Прайс-лист модели — отдельная оценочная величина, не подмена фактической стоимости. Если нет надёжных usage/cost — `не определено`, а не 0.
2. **Логическая состоятельность (%).** Отдельная исследовательская оценка: соблюдение условий задачи, отсутствие противоречий, качество контраргумента и критериев пересмотра решения. Для оценки указать конкретные выдержки/ссылки на ответы и объяснение. Не выводить процент автоматически из технического `accepted`.
3. **Соответствие Алетеону (%).** Отдельная исследовательская оценка сходимости с **замороженными контрольными ответами Алетеона C**, с указанием версии/источника контроля и оснований оценки. Совпадение окончательного решения само по себе не означает высокой сходимости рассуждений. Эта оценка **не зависит** от оценки логической состоятельности.
4. **Краткий вывод.** Одно-два предложения о характерных сильных/слабых сторонах ответа, нарушенных ограничениях и существенных отличиях от C. Отделять наблюдение от интерпретации.

Если содержательных данных недостаточно, для каждой отсутствующей оценки явно писать `не оценено` с причиной. Не придумывать проценты и не заменять отсутствие данных нулями. Ранее выставленные оценки помечать как предварительные субъективные, если отсутствовала формальная слепая процедура.

## Структура нового отчёта

Каждый новый отчёт — `derived/EXP-<id>-REPORT.md` (например, `EXP-1.3-REPORT.md`). Включает:

- ID эксперимента, дату подготовки отчёта, ID запуска(ов), идентификаторы моделей, версию протокола и ссылки на исходные файлы в `runs/`.
- Таблицу: **модель | фактическая USD/token (и USD/1M) | логическая состоятельность (%) | соответствие Алетеону C (%) | краткий вывод**.
- Для каждой модели: проверяемые данные расчёта цены, основания двух независимых оценок по H1/H2, ограничения интерпретации и источники.
- Статус: завершённый/частичный/заблокированный; техническое принятие 4/4 указывать отдельно от смысловой оценки.
- Краткий итог эксперимента: различия между моделями, что выяснили и чего из этих данных заключить нельзя.

Сравнения разных экспериментов допустимы только с оговоркой об изменениях моделей, контекста, вопросов и методики. Не приписывать различия цене или загрузке Алетеона без соответствующего контролируемого сравнения.

## Сводный график в чате после каждого эксперимента

После подготовки каждого нового отчёта **ассистент вручную строит и показывает в текущем чате обновлённый сводный график** по всем экспериментам, для которых есть достоверные оценки и сведения о стоимости. Это обязательная часть разбора результатов, а не задача Runner и не автоматически генерируемый файл.

- На одном сравнительном графике для каждой пары «эксперимент — модель» показывать **соответствие Алетеону C (%)**, **логическую состоятельность (%)** и **среднюю фактическую стоимость 1 млн токенов (USD)**.
- Использовать **две отдельные оси Y**: проценты 0–100 для двух оценок и USD/1M tokens для стоимости. Не нормализовать цену к процентам и не смешивать единицы.
- Подписывать модели и ID экспериментов; обновлять график накопительно после каждого эксперимента, сохраняя прежние проверенные результаты.
- Если для модели отсутствует показатель, не изображать его нулём; явно обозначить пропуск. Не выдумывать оценки или цены.
- График **показывается непосредственно в чате**, а не только сохраняется в репозитории. Ассистент создаёт его вручную по данным отчётов; автоматическая генерация в Runner не требуется.
- Кратко объяснять выявленные различия и ограничения сопоставимости экспериментов.

## Правила обновления и архивации

- Не переписывать исторические оценки без следа: при исправлении указывать, что изменилось и почему; старую версию сохраняет Git.
- Если создаётся новая сводная версия отчёта, предыдущую сводку и связанные с ней изображения переносить в `derived/Depricated/`, сохраняя относительные ссылки.
- Новые аналитические оценки не являются частью `protocol.json`, `rotation.json` или `rotation-state.json`. Не использовать их для выбора очередной группы.
- Отчёт формируется **после получения исходных результатов**. Не добавлять автоматический оценщик в Runner: логическую состоятельность, соответствие C и краткий вывод вручную формирует ассистент после анализа каждого эксперимента.
